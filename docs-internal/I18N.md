# Internationalisation

The site ships **fully-rendered HTML per language**. There is one template per
route and one catalogue per language; the copy is merged in at build time.

```
pages/tarifs.html          template (French, with data-i18n markers)
i18n/fr.json  en.json  de.json   the copy
        |
   npm run build:pages
        v
docs/fr/tarifs/  docs/en/tarifs/  docs/de/tarifs/
```

No text is swapped in the browser, so there is no flash of untranslated content
and search engines index each language at its own URL.

Before this, every page existed three times over (`pages/`, `pages/en/`,
`pages/de/`) and the three copies had already drifted apart. Those directories
are gone; their translations live in `i18n/*.json`.

## Editing copy

Change the value in `i18n/<lang>.json` and reload — `server.js` renders on each
request and re-reads a catalogue whenever its mtime changes, so no restart and
no build are needed in development. Run `npm run build:pages` before deploying.

## Markers

Markers are attributes added to existing tags. They never alter the copy in the
template, so `pages/*.html` stays a valid, directly viewable French page.

| Marker | Applies to | Example |
| --- | --- | --- |
| `data-i18n="key"` | element whose content is one plain string | `<h2 data-i18n="faq.body.title">Questions</h2>` |
| `data-i18n-rich="key"` | element mixing text and inline markup | see below |
| `data-i18n-attr="alt:key\|title:key2"` | translatable attribute values | `<img alt="Logo" data-i18n-attr="alt:index.body.logo_alt">` |
| `data-i18n-raw="key"` | a `<script type="application/ld+json">` body | schema.org data, translated per language |
| `data-i18n-js="page.js"` | empty `<script>`; receives that catalogue branch | exposes `window.t()` to inline scripts |

### Rich units

Word order moves around inline markup, so a whole sentence is one unit and the
inline children become numbered placeholders:

```html
<h1 data-i18n-rich="telecharger.body.download">
  Téléchargez l'application <span class="text-brand-500">Rainbow</span>
</h1>
```
```json
"fr": "Téléchargez l'application <0>Rainbow</0>",
"en": "Download the <0>Rainbow</0> app",
"de": "Laden Sie die <0>Rainbow</0> App herunter"
```

`<0>` binds to the first inline child **in the template**, so classes and
attributes live in exactly one place — translators only ever see words.

### Strings inside inline scripts

Copy built by JavaScript (the partner locator's labels, the webinar form modals,
the comparison-table toggle) cannot carry an attribute. Those pages declare the
branch they need and then call `t()`:

```html
<script data-i18n-js="trouver-un-partenaire.js"></script>
...
{ n: ALL.length, l: t('statPartners') }
```

The branch is inlined at build time, so there is no runtime fetch. `t(key, fallback)`
returns the key itself if nothing matches.

## Key naming

`<page>.<zone>.<slug>` — zone is the enclosing `<section id>`, or `nav`/`footer`,
or `body`. Strings in the nav and footer are shared across pages under
`common.nav.*` / `common.footer.*`, so they are translated once. Page metadata
uses `<page>.meta.{title,description,schema}`.

## Tooling

| Command | Purpose |
| --- | --- |
| `npm run build:pages` | render all languages into `docs/` |
| `node tools/i18n-add-js-keys.js` | (re)add the `<page>.js.*` branches; idempotent |

`tools/i18n-extract.js`, `i18n-verify.js` and `i18n-diff.js` were the one-shot
migration: they harvested the catalogue out of the old `pages/en/` and
`pages/de/` trees and proved the result byte-for-byte equivalent (28 renders, no
differences). Those trees are gone, so the three tools no longer have inputs.
They are kept because they document how the catalogue was derived, and they are
the starting point if the same migration is ever needed for another page set.
Day to day you only edit `i18n/*.json` and run the build.

`tools/i18n-lib.js` holds the scanner. It is deliberately not a real HTML parser:
parse5/jsdom would re-serialize and silently reformat every page. The scanner
returns byte ranges and rendering splices over them, so anything untranslated
comes out exactly as authored.

A key referenced by a marker but absent from a catalogue leaves the source copy
in place and makes `build:pages` print a warning — check the build output.

## Adding a language

1. Copy `i18n/fr.json` to `i18n/<lang>.json` and translate the values.
2. Add the code to `LANGS` in `server.js`, `tools/build-pages.js` and
   `tools/i18n-extract.js`, and to the switcher in `js/i18n.js`.
3. Add its nav words to `COPY` in `js/mega-menu.js` (that file carries the
   mega-menu's own copy).

## Known gaps

- `pages/form-ale.html`, `pages/confirmer-rendez-vous.html`,
  `pages/modifier-rendez-vous.html` and `pages/desinscription.html` are one
  shared file across all languages and still translate themselves
  **client-side** from tables embedded in each file. They are served as
  authored and are not part of this pipeline.
- `i18n/archive/*.legacy.json` holds the previous catalogue, which described an
  older app (portal, checkout, login, offers). Nothing references it; it is kept
  only so the copy is not lost.
